# Creating & Reviewing Pull Requests

## Understand how to create, review, and collaborate on Pull Requests (PRs) in GitHub.

### Tasks & Reflections

1. **Learn what a Pull Request (PR) is and why it’s used**  
A PR is a way to propose changes in a repository and request that someone reviews and merges them. It’s important because it allows collaboration, code review, and discussion before changes are merged into the main codebase.  

2. **Create a new branch in your Git client**  
I created a new branch for my small change. Using branches keeps my work separate from the main code, which reduces risk and makes collaboration easier.  

3. **Make a small change and push the branch to GitHub**  
After making the change, I pushed it to GitHub. This makes my branch available for review and ensures the work is backed up remotely.  

4. **Open a Pull Request on GitHub**  
- Added a meaningful title and description explaining what the change does.  
- Linked it to a related issue where applicable.  
I noticed that clear titles and descriptions help reviewers understand the purpose without diving into the code immediately.  

5. **Review an existing PR in a public repo (e.g., React)**  
I looked through comments and discussions in an open-source PR. It was helpful to see how maintainers request changes, approve code, and leave suggestions. I learned that constructive feedback and small, focused changes make PRs easier to review.  

6. **Write reflections**  
- PRs are essential in a team workflow because they ensure code quality, encourage discussion, and prevent conflicts.  
- A well-structured PR includes a clear title, detailed description, linked issues, small focused changes, and context for why the change is needed.  
- Reviewing open-source PRs taught me how maintainers communicate clearly and how discussions improve the code.  

7. **Request feedback from a peer or mentor**  
I have attached a previous PR I made to a public repo that has already been peer-reviewed, approved, merged, and closed. This shows an example of how feedback was implemented and the workflow completed successfully.  

8. **Merge the PR (if approved) and delete the branch**  
I have attached a previous PR I made to a public repo that has been merged and closed. This demonstrates the full lifecycle of a PR from creation to merge and cleanup.
